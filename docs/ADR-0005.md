# ADR-0005: Managed Supabase Auth and scoped PostgREST adapter

Date: 2026-11-02. Status: Adapter implemented, **shared-project staging only; no public launch**.

## Environment and isolation

The Prysm Style Supabase project `dpcpbebiylwozvkjubeq` was explicitly authorized as a fallback by the owner. It contains an existing `on_auth_user_created` trigger that writes new Auth users to Prysm's `user_profiles` table. Reusing it for Priorly registration would mix products. Therefore, the Priorly server **refuses to start its Auth integration** when `SUPABASE_URL` is Prysm Style's URL. Prysm was used strictly to stage the six prefixed, owner-scoped `public.priorly_*` database tables, with their RLS policies; we did not create Auth users or modify Prysm tables/functions/triggers. The SQL migration remains available for later use in a separate Priorly instance.

## Backend adapter

`server/supabase-store.mjs` implements the existing app persistence interface using Supabase Auth and REST/PostgREST. Registration and login delegate password handling to Supabase Auth. The API server stores access and refresh tokens in HttpOnly, SameSite=Strict cookies, and checks the session via `/auth/v1/user`; expired sessions may be refreshed with `/auth/v1/token?grant_type=refresh_token`. API requests access rows with that **same end-user bearer token**, allowing database RLS to enforce authorization. No service_role or secret key is used in frontend code or server data access. Only the publishable API key is required; keep it in process environment.

The adapter supports user-scoped projects, research runs, evidence, technical claims, review classifications and claim-source links. Project IDs are validated, and source links are checked in the same project. Supabase Auth email confirmation produces a pending verification message rather than assuming a logged-in session.

## Limitations to resolve before public launch

- No dedicated Priorly Supabase project is connected; no live end-to-end Supabase Auth test, real multi-user session test or production deployment.
- Existing app's localhost-only release guard is retained; `NODE_ENV=production` and non-loopback binding are intentionally rejected.
- Cookie sessions require further threat modeling, concurrency-safe refresh, password reset, MFA, verified CORS/origin enforcement and a managed TLS deployment plan.
- PostgREST calls are not an atomic multi-table transaction; research runs can be saved before evidence ingestion fails. Error states are explicit, and a job/transaction orchestration layer is required.
- No encryption of user-supplied confidential documents, managed backup/restore, data retention controls, or external penetration test has been completed.
- OpenAlex and GitHub retrieval is not a complete patent or market novelty analysis.
- **Do not submit unpublished inventions or private agreements yet.**

## Deployment decision

Provision a dedicated Priorly Supabase project using a cost-authorized organization. Apply the schema, verify two distinct Auth users and all RLS policies, run security advisors, then complete authentication recovery, auditing, protected storage and deployment QA before releasing to real customers.
