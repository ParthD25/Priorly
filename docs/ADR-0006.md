# ADR-0006: Priorly on the existing Prysm Style Supabase database

Date: 2026-11-02. Status: shared-database development integration enabled; no public hosting.

The user explicitly authorized building Priorly on top of the existing Prysm Style database. The `public.priorly_*` tables have already been created using a reviewed, owner-scoped RLS migration. The database contains other Prysm product tables; none are modified, renamed or deleted by this phase.

## Authentication boundary

Prysm Style uses **the same Supabase Auth users**. It has an `on_auth_user_created` trigger that automatically creates a `public.user_profiles` record for every new Auth signup. Therefore, Priorly may use existing accounts during development, but **Priorly registration is disabled** when connecting to this shared project. This avoids unintended Prysm profile creation from a Priorly signup. No Prysm trigger, function or existing account is modified.

The server will only accept a shared Prysm Supabase URL if `PRIORLY_USE_SHARED_SUPABASE=true` is explicitly set. The process still binds to localhost and refuses `NODE_ENV=production`. The landing workspace shows existing-account login only when shared auth is enabled. Registration is also blocked server-side (403), not just hidden in the UI.

## Isolation

Every Priorly-owned project, claim, evidence row, comparison and research run has a dedicated `priorly_*` table with RLS scoped to `auth.uid()` and composite owner/project foreign keys. Supabase users are shared, but **project records are separate**. A Prysm account does not automatically see anyone else's Priorly projects. This is not full application-identity separation, and should be documented when onboarding users.

## Operations

Copy `.env.example` to `.env`, supply the *publishable* project key, and run `npm run dev:shared` on Node 22. The publishable key is not a service-role key and should never be substituted with a secret. Existing Prysm test users can sign in. No production deployment or private user uploads are authorized.

Before launching as a separate public product, move Auth to an isolated tenant or plan for deliberate shared-account lifecycle, with account deletion, email confirmation, security reviews and incident response. Supabase Auth user deletion in this shared project may also affect Prysm profiles. **Never implement deletion without cross-app impact analysis.**

Limitations: no live user login is tested in this chat because user credentials are not available; automated mock Auth tests and live schema/RLS audits are possible without creating test users. Localhost-only safeguard remains active.
